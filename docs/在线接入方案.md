## 一、当前在线链路（待替换）

`/api/recommend` 现状：读 `user_profile.interest_tags` → 品类内热度 Top-K + 品类外热度 Top-K
→ `rank.py` 做 `0.3·热度 + 0.7·品类内名次` 融合 → α 重排。

**与离线 ours 算法不同源**，且无冷区注入。

## 二、接入后在线链路（目标）

```
用户历史（behavior 表）
  → UserCF / ItemCF 召回
  → OursScorer.build_pool（含冷区注入）      ← 与离线同一函数
  → OursScorer.score["ours"]                 ← 与离线同一函数
  → diversity.rerank(α)                      ← 已共用
  → 返回 + 标冷区来源
```

## 三、实测数据（决定方案取舍）

| 项 | 实测值 | 来源 |
|---|---|---|
| 单请求耗时（候选池组装 + ours 打分 + 1 次 α 重排） | **18.9 ms** | `$TEMP/probe_online_latency.py`，n=300 |
| QPS 上限（单核串行） | 52.8 req/s | 同上 |
| 内存增量（加载 CF + 统计） | **+5.2 GB** | 同上 |
| CF 初始化 | 11.2 s（全量脚本含冷区诊断时 56 s） | 探针 / eval_v6.log |

**结论：延迟不是瓶颈，可以实时跑，不需要预计算绕路。真正的问题是内存与数据源。**

## 四、必须解决的三个约束

### 约束 1：模型数据不在 MySQL 里

`OursScorer` 与 CF 依赖三份**离线产物文件**（不在任何库中）：

| 依赖 | 来源文件 |
|---|---|
| pop / cat_top / 冷区类目 / global_top | `data/splits/jdsearch_eval/stats_cache.parquet` |
| UserCF / ItemCF | `data/splits/jdsearch_eval/cf_pairs_2000.parquet` |
| 商品→类目 | MySQL `item.category_id`（或由 `cat_item` 近似推导） |

⇒ 在线服务启动时需**读 parquet**，不是查库。服务与评估脚本须部署在同一台机器（或共享该目录）。

### 约束 2：双库 —— 演示库 vs 真实库

| | `shoprec_test`（当前演示） | `shoprec_jd`（真实数据） |
|---|---|---|
| 规模 | 40 商品 / 2 用户 / 33 条 behavior | 503 万商品 / 2667 万交互 |
| 商品图 | 有（9300001~9300120 示意图，120 商品 8 类目） | 无 |
| 冷区类目 | **几乎不存在**（交互量远达不到 [20,100)） | 1,026 个 |
| CF 可学性 | **学不出**（33 条行为） | 可学 |

**关键矛盾**：CF 模型必须用 `shoprec_jd` 才有意义，但演示库商品 ID 不在 CF 索引里
（`ucf.recommend` 查不到演示商品 → 候选池近乎为空 → 冷启动演示失效）。

**三条出路**：

| 出路 | 做法 | 评价 |
|---|---|---|
| **A. 在线直连 `shoprec_jd`** | 演示切到真实库；前端按品类把 40 张示意图映射到真实商品 | 🟢 **推荐**：算法完全真实、冷区注入真生效、内存 5.2GB 可接受。图仍标"示意图，非数据集内容" |
| B. 演示库上重建小规模 CF | 在 `shoprec_test` 的 33 条行为上跑同一套代码 | 🟡 代码同源但**冷区类目不存在**，冷启动演示仍看不到；只解决"同源"，不解决"冷启动可见" |
| C. 预计算 jd 结果映射到演示商品号 | 离线在 jd 跑，结果套到演示商品号上 | 🔴 **不可取**：演示商品不是 CF 真推出来的，属套壳，答辩被追问会穿帮 |

### 约束 3：内存 5.2 GB

缓解手段（按代价递增）：
1. **独立模型进程**：CF 常驻一个进程，API 通过本地 HTTP/队列取分 —— 崩溃隔离，API 重启不必重载
2. **降 `top_m`**：`ItemCF(top_m=15000)` 的 15000×15000 矩阵是内存大头，降到 5000 可省 ~1.5GB，**但会改变离线指标**（须重跑，违反冻结）——🔴 不可取
3. 演示前关掉无关 MCP 服务

⇒ 采用方案 1，不动模型参数。

## 五、推荐落地步骤

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | 新增 `src/api/services/model_loader.py`：启动/首次请求时加载 parquet + CF，构造 `OursScorer` 单例 | 启动 11 s，可改为懒加载 |
| 2 | `/api/recommend` 改为读 `behavior` 表用户历史 → `build_pool` → `score` → `rerank` | 中 |
| 3 | 演示切到 `shoprec_jd`，前端加品类→示意图映射表 | 低 |
| 4 | 端到端验证：接口返回的推荐中**必须出现冷区商品**（source 标注） | 这是验收判据 |

**验收判据（可证伪）**：`SELECT` 若干冷区类目商品，确认 `/api/recommend` 返回结果中包含它们。
若不包含 ⇒ 冷启动在线上仍未生效，不得在答辩中声称。

## 六、明确不做

- ❌ 改 `ItemCF(top_m)` / `CF_ITEMS` / `COLD_BOOST` 等参数 —— 会改变已冻结指标
- ❌ 在线另写一套打分 —— 违背本次重构的目的
- ❌ 预计算结果套壳到演示商品号（出路 C）
