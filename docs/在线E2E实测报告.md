## 2. 接口耗时（浏览器内 `fetch` + `performance.now()`，21 次采样）

| 接口 | 中位数 | min | max | 说明 |
|---|---|---|---|---|
| `recommend k=0`（不写日志） | **15.3 ms** | 13.9 | 16.0 | 纯算法耗时 |
| `recommend k=10` | **84.8 ms** | 81.3 | 100.3 | |
| `recommend k=40`（页面默认档） | **249 ms** | 224.8 | 259.6 | |
| `feedback`（写一条行为） | **24.1 ms** | 21.9 | 26.3 | |

**耗时模型**：`T ≈ 15ms + k × 5.8ms`（线性拟合极佳）。

### 🔴 关键发现：k=40 时 94% 的时间在逐条写推荐日志

k=40 的 249ms 里，约 **234ms（94%）是 40 次逐条 `INSERT recommend_log`**；
纯算法只有 15ms。根因是 `repo.execute` 每次调用都 `begin()` 一次，
即**一条 INSERT 一个事务**（一次网络往返 + 一次提交）。

### ✅ 已修复（2026-10-13 19:40，提交 `5424d69`）

`repo.execute_many()` 改为**单事务批量写入**（PyMySQL 自动合并为多值 INSERT）。

**严格同口径微基准**（40 行写入，5 次中位数）：

| 方式 | 耗时 |
|---|---|
| 逐条（40 次单事务） | **276.6 ms** |
| 批量（1 次事务） | **8.0 ms** |
| **加速** | **34.6 倍** |

**端到端复测**（浏览器内 fetch，21 次中位数）：

| 接口 | 优化前 | 优化后 |
|---|---|---|
| `recommend k=10` | 84.8 ms | **22.5 ms** |
| `recommend k=40` | 249 ms | **21.8 ms** |
| `recommend k=0` | 15.3 ms | 12.1 ms |
| `feedback` | 24.1 ms | 24.9 ms（未改动） |

> 口径说明：k=40 前后返回的条数不同（34 → 20，因测试用户在计时过程中又产生
> 了点击行为、候选池变窄），故端到端倍数不严格可比；**上表的数据库层微基准
> 才是严格同口径**，34.6 倍是可靠数字。

## 3. 推荐变化：购买前 vs 购买后

| | 购买前（无行为） | 购买后（点+买了 9300001 数码家电） |
|---|---|---|
| 商品数 | 40 | 34（测试当时）→ 20（20:06 复看，见下注） |
| 推荐标记 | 全部「热门」 | 「双路融合」(fused) / 「跨品类迁移」(aux) |
| 内容 | 跨类目混合（手机/牛仔裤/红酒/扫地机…） | **数码家电占据头部**（第 1、5、8 位…），但牛仔裤、红酒等仍保留 |
| 召回来源 | 全局热门兜底 | 双域召回 + 融合排序 |

**解读**：行为后推荐正确响应——交互过的类目（数码家电）分数被抬高、占据头部；
同时 α 品类多样性重排仍在起作用（非数码类商品保留在后位），没有退化成"只推同类"。
这正是答辩可以现场演示的闭环：**注册 → 冷启动兜底 → 一次行为 → 推荐即时个性化**。

## 4. 结论

1. **链路功能层面完全可用**，冷启动 → 个性化闭环成立，可放心放进答辩演示。
2. **性能短板明确且好修**：逐条写日志吃掉 94% 延迟；批量写是一行级改动，
